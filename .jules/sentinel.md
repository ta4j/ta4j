## 2026-10-15 - Deserialization Domain Invariant Validation in `readObject`
**Vulnerability:** Standard Java deserialization (`readObject`) bypasses constructors, allowing serialized payloads with negative `volume`/`amount`/`trades` or null timestamps/periods to instantiate invalid domain objects (`BaseBar`).
**Learning:** Adding validation in `readObject` throwing `InvalidObjectException` enforces domain constraints on deserialized objects without impacting valid serialized instances.
**Prevention:** Any `Serializable` class in ta4j implementing `readObject` must validate all constructor domain invariants.
## 2026-10-19 - Java Deserialization Invariant Validation for Serialized BarSeries
**Vulnerability:** `BaseBarSeries.readObject()` re-initialized transient fields like the logger but did not validate deserialized object invariants, allowing corrupted payloads (e.g. null `bars`, `numFactory`, `barBuilderFactory`, or out-of-bounds series indices) to deserialize into invalid object states.
**Learning:** In Java serialization (`ObjectInputStream`), `defaultReadObject()` populates fields directly without invoking constructors or factory validations.
**Prevention:** Always implement a private `validateDeserializedState()` helper in `readObject()` and throw `java.io.InvalidObjectException` if deserialized fields violate structural invariants.
## 2026-10-21 - Path Traversal via Cache File Notes Parameter
**Vulnerability:** Unsanitized `notes` parameter in `AbstractHttpBarSeriesDataSource` cache file path generation allowed path traversal sequences (`..`, `/`, `\`) to write or read cache files outside the configured `responseCacheDir`.
**Learning:** String parameters appended to cache filenames (like optional notes or labels) can act as path traversal vectors if concatenated without sanitization or path boundary validation. Replacing disallowed characters with a placeholder stops the traversal but lets distinct inputs collide on one cache file (`run/a` and `run a` both became `run_a`), so one run could be served another run's cached data.
**Prevention:** Encode user-supplied filename components injectively instead of replacing characters: percent-encode every byte outside a lowercase allowlist (`[a-z0-9_-]`; `%`, `.`, uppercase letters and path separators are always escaped, so names also stay distinct on case-insensitive file systems), and still perform path boundary checks using `resolvedPath.normalize().startsWith(baseDir.normalize())`.

## 2026-10-27 - Deserialization Domain Invariant Validation in `BaseTradingRecord`
**Vulnerability:** `BaseTradingRecord.readObject()` and nested `PositionBook.readObject()` re-initialized transient lock and cost models but did not validate structural invariants, allowing corrupted payloads with null `startingType`, `matchPolicy`, or `positionBook`, or negative `nextTradeIndex`/`nextSequence` to instantiate invalid objects.
**Learning:** In Java serialization, `defaultReadObject()` sets fields directly without constructor checks. For composite state objects with internal ledgers (like `PositionBook`), deserialization checks must validate both the outer container and inner state objects. A check must also never be stricter than the constructors: a `BarSeriesManager` run window that does not overlap the series produces `startIndex > endIndex`, which the constructors accept, so that empty window must stay deserializable.
**Prevention:** Always validate non-null requirements, non-negative counters, and nested container state in `readObject()`, throwing `java.io.InvalidObjectException` when invariants are violated, but never reject states the constructors or runtime can legitimately produce. Cover rejected states with malformed-stream tests and supported edge states with round-trip tests.
## 2026-10-28 - Java Deserialization Invariant Validation for Serialized BaseTrade
**Vulnerability:** Standard Java deserialization (`readObject`) bypasses constructors, allowing serialized payloads with trade indices below -1 or null required fields (type, price, amount, cost, netPrice, fills) to instantiate invalid `BaseTrade` domain objects. Scalar trades may have zero or negative amounts, and index -1 represents deferred assignment.
**Learning:** `BaseTrade` implements `Serializable` but lacked `readObject` validation. Validating fields in `readObject` and throwing `InvalidObjectException` prevents corrupted streams from instantiating invalid trades.
**Prevention:** Any `Serializable` domain model in ta4j must implement `readObject` to validate all constructor invariants upon deserialization.

## 2026-10-29 - Invariant Validation in BarBuilderFactories and BarBuilders
**Vulnerability:** `TickBarBuilderFactory`, `VolumeBarBuilderFactory`, and `AmountBarBuilderFactory` did not validate constructor parameters or deserialized object states, allowing zero/negative thresholds or null policies to cause arithmetic division-by-zero errors or invalid bar calculations when ingesting trade data.
**Learning:** `BarBuilderFactory` implementations are `Serializable` components used by `BarSeries`. Because deserialization restores primitive fields directly without constructor checks, factory thresholds must be validated in `readObject()` throwing `InvalidObjectException`.
**Prevention:** Every `BarBuilderFactory` and `BarBuilder` class with threshold limits or policy configurations must validate positive values (`threshold > 0`) and non-null enum references in constructors and `readObject()` methods.
